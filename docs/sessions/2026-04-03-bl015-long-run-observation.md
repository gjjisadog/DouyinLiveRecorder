# 2026-04-03 BL-015 长时间边界补观察

## 这次做了什么
- 基于已经修复的打包版客户端，补了一轮更长时间的真实录制观察。
- 目标不是再次证明“能切段”，而是观察：
  - 多轮切段是否持续稳定
  - 历史记录是否持续正确落档
  - 阈值控制精度在更长样本下是否恶化

## 实际执行
```powershell
.\.client-conda-env\python.exe scripts/exe_automation_acceptance.py `
  --workspace tmp_bl015_long_run_observation `
  --display-name BL015_Long_Run `
  --record-seconds 75 `
  --max-file-size-gb 0.001 `
  --poll-interval 1.0 `
  --command-timeout 25
```

## 关键产物
- 摘要：`tmp_bl015_long_run_observation/acceptance_summary.json`
- 录制文件：
  - `BL015_Long_Run_2026-04-03_10-20-28_000.ts`
  - `BL015_Long_Run_2026-04-03_10-20-57_000.ts`
  - `BL015_Long_Run_2026-04-03_10-21-24_000.ts`

## 已确认事实
- 观察参数：
  - `record_seconds=75`
  - `max_file_size_gb=0.001`
  - 阈值折算为 `1073741` bytes
- 75 秒内稳定切出 3 段。
- `rollover_detected=true`
- 历史记录稳定增长到 3 条，且 `file_path` 全部是实际 `_000.ts` 文件路径。
- 三段文件大小分别为：
  - `1901432`
  - `1877744`
  - `736960`

## 观察结论
- 连续切段稳定性通过。
- 历史落档稳定性通过。
- 阈值精度没有达到“接近阈值即切”的程度：
  - 最大超限偏差 `827691` bytes
  - 相比 `BL-014` 的小阈值样本，这一偏差更大

## 当前推断
- 当前实现已经满足“长时录制不会一直堆到单一文件里，能持续切到下一段”。
- 但它更像“周期性检查后切段”，不是“严格按目标阈值附近切段”。

## 结论
- `BL-015` 已完成。
- 现阶段可以确认：
  - 自动切段功能可用
  - 长时间连续切段链路稳定
- 现阶段不能确认：
  - 文件大小能被控制在非常接近目标阈值的位置

## 下一步建议
1. 如果业务目标只是“避免单文件无限变大”，当前链路已经够用。
2. 如果业务目标是“尽量贴近 1GB 再切下一段”，应继续做 `BL-016`，专门优化阈值精度。
